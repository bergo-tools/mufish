# REQ-006 代码审查问题修复

## 背景

2026-10-22 对当前代码做了一轮从后端到前端的完整审查。现有测试（`go test ./...`、前端纯函数测试、组件测试）全部通过，`go vet`、`go build` 也通过，但审查中仍发现多处会影响账务、库存、权限可信度和日常操作体验的问题。

其中 7 个问题已用临时回归测试实际复现（测试文件在验证后已删除，未进入仓库）：

1. 往来单位列表的应收/应付恒为 0；
2. 「往来冲抵」仍然修改资金账户余额；
3. 作废已被销售消耗的采购单会把库存冲成负数；
4. 内置角色被移除的权限在重启后被 seed 重新加回；
5. 负单价可以保存并入库；
6. 本月销售/采购/毛利会把未来月份的单据计入；
7. 未指定仓库时默认仓库的 `warehouse_id` 写成 0。

这些问题说明当前测试对“边界、回滚、重启持久化、跨期口径”的覆盖不足。本需求用于集中登记、分批修复并补齐回归测试。

## 用户故事

- 作为财务/老板，我希望应收应付、账户余额、库存成本和本期报表始终准确，避免错账。
- 作为仓管/销售，我希望开单、盘点、调拨不会在无提示的情况下产生负数或漏掉商品。
- 作为系统管理员，我希望角色权限、系统设置和接口权限真实生效且重启后保持。
- 作为维护者，我希望每个修复都有能复现问题的测试，后续改动能被回归测试拦住。

## 优先级与范围

- **P0（必须修）**：会直接算错账、丢数据或破坏权限可信度，已复现的问题全部在这一档。
- **P1（本版本应修）**：权限边界、报表口径、明显的静默截断和持久化问题。
- **P2（记录，完成 P0/P1 后再决定是否纳入本版本）**：交互优化、文案、可访问性和非阻塞的功能取舍。

> P0/P1 是本需求的验收范围；P2 先在本文档留档，避免遗漏，不阻塞 v0.4.0 的 P0/P1 交付。若确认要一起做，再把对应 P2 条目移入验收标准。

## 实现方案

- **影响范围**：`internal/store`（余额、库存冲销、角色 seed、报表）、`internal/api`（权限、参数校验、导出/导入）、`web/src`（登录/会话、路由、列表错误态、表单校验、盘点/选择器）、`README.md`、`main.go`。
- **数据模型 / 数据库变更**：P0 预计不需要改表。若 P1-20 采用调整单或审计字段，需要修改 `schema.sql`，并在本文档注明“需要重建开发库”；测试必须使用 `t.TempDir()` 新库。
- **API 变更**：新增参数校验和权限校验；报表明细补单据号/日期；截断接口返回总数或截断标记；不破坏现有成功响应结构。
- **前端变更**：登录/401 全局处理；路由权限；列表错误态；盘点全量加载与商品搜索；导出错误反馈；弹窗未保存确认。
- **测试计划**：
  1. 每个 P0 先写失败测试，复现后修复，再确认通过；
  2. 金额、库存、作废、删除余额类改动必须包含“失败不改变数据”的回滚断言；
  3. RBAC 改动覆盖有权限、无权限、超级管理员三种场景；
  4. 报表口径覆盖月初、月末、跨月、跨年、未来日期；
  5. 前端至少补登录落地、401、路由权限、报表切换筛选的组件测试；
  6. 完成后跑 `go test -race -count=1 ./...`、`make test-all`、`make vet`、`make web`，核心流程补充 `make test-e2e`。
