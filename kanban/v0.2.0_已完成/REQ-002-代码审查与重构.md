# REQ-002 代码审查、缺陷修复与必要重构

## 背景

项目已完成 v0.1.0，但在开发过程中发现若干可疑点：自动编码可能造成数据库连接阻塞、应收应付口径与报表不一致、进销存汇总的期末数取自当前库存而非查询期末、收付款关联单据缺少类型与往来单位校验等。需要在补测试的同时做一次系统性的代码检查，修复真实缺陷并清理不合理实现。

## 用户故事

作为项目维护者，我希望对现有代码做一次完整审查，修复影响数据正确性和稳定性的缺陷，并清理明显的死代码与不一致实现，以便后续版本建立在可靠的基础上。

## 验收标准

- [x] 修复自动编码函数在单连接 SQLite 下可能阻塞的问题，并补测试。
- [x] 修复应收应付余额把草稿单据计入的问题，统一为仅统计已确认单据。
- [x] 修复进销存汇总的期初金额、期末数量和期末金额口径，保证按查询区间计算且日期边界包含结束日当天。
- [x] 修复销售排行成本金额整数除法精度问题。
- [x] 收付款关联采购/销售单时校验单据类型、单据状态和往来单位归属。
- [x] 采购/销售单校验往来单位类型与仓库可用状态。
- [x] 更新基础资料时，空编码保持原编码而不是写入空字符串。
- [x] 分类维护阻止把父级设置为自己的下级，避免树形成环。
- [x] 清理确认采购时未使用的 `strict` 变量、删除用户时未使用的计数等死代码。
- [x] 所有修复附带回归测试，`make test`、`make vet`、`make web` 全部通过。
- [x] 在本文档记录已修复项与暂不处理的遗留问题及原因。

## 实现方案

- 影响范围：`internal/store`、`internal/api`、`internal/model`（如有必要）、`web/src`（仅测试）。
- 数据模型 / 数据库变更：不新增表；如发现口径问题，优先在查询层修复，避免破坏已有数据。
- API 变更：仅增加参数校验和错误返回，不改变成功响应结构。
- 前端变更：无运行时行为变更。
- 测试计划：每个修复先写失败测试，再修复，最后回归全部测试。

- 已修复缺陷清单：
  1. **自动编码阻塞（严重）**：`nextSimpleCode` 在未关闭 Rows 的情况下继续查询，单连接 SQLite 会等待同一连接，导致商品/客户/供应商/仓库/账户“留空自动生成编码”永久阻塞。改为 QueryRowContext，并补超时回归测试。
  2. **采购/销售关键字查询 SQL 错误（严重）**：`docFilter` 同时引用 `o.supplier_name` 和 `o.customer_name`，采购表没有客户字段、销售表没有供应商字段，任何关键字搜索都会报 `no such column`。改为按单据类型传入往来单位字段。
  3. **分类树丢失子节点（严重）**：`ListCategories` 在子节点挂接前就复制了根节点值，父节点先于子节点排序时 children 永远为空。改为先完成挂接再复制，并补三级分类测试。
  4. **应收应付把草稿计入（严重）**：`PartnerBalance` 使用 `status<>2`，草稿单据会虚增应收应付。改为 `status=1`。
  5. **进销存期末取当前库存（严重）**：历史区间查询会显示今天的库存。改为期末 = 期初 + 本期入库 - 本期出库；期初金额按出入库方向汇总；结束日按 23:59:59 包含当天。
  6. **销售排行无法扫描 + 成本截断（严重）**：`SUM(cost_price * qty / 100)` 返回浮点且逐行截断，扫描 int64 直接报错。改为 CTE 汇总后四舍五入到分。
  7. **收付款可关联错误单据（严重）**：收款可关联采购单、付款可关联销售单、收款单位可与销售单客户不一致。保存和确认两处都增加类型/状态/往来单位校验。
  8. **采购/销售可任选往来单位或停用仓库（中）**：采购单可选择客户、销售单可选择供应商，停用仓库也能用于新单据。改为按角色校验 supplier/customer/both，并拒绝停用仓库。
  9. **空编码更新写入空字符串（中）**：编辑商品/客户/仓库/账户时清空编码会把唯一编码写成空。改为保留原编码，并在目标不存在时返回 ErrNotFound。
  10. **分类可形成环（中）**：只校验“父级不能是自己”，仍可把父级设为孙级。增加父级存在性与后代递归校验。
  11. **零库存商品不进入预警（中）**：预警只查 `stocks`，从未入库或已清零的商品永远不出现。改为 products LEFT JOIN stocks，同时支持“全部仓库”和单仓口径。
  12. **盘点按陈旧账面调整（中）**：保存盘点后若又发生出入库，完成盘点会按旧差异调整。完成前校验当前库存与盘点时账面一致，不一致则要求重新盘点；并拒绝重复商品、负数实盘。
  13. **调拨总额不随实际成本更新（中）**：确认调拨时明细成本已更新，但表头 total_amount 仍是保存时输入值。确认时按实际结转金额回写。
  14. **无效备份恢复后 Store 关闭（中）**：恢复损坏文件后 `Open` 失败，Store 停留在已关闭状态。改为先校验回滚副本，失败时自动回滚并重新打开。
  15. **导出超过 500 行被截断（中）**：商品导出和库存流水导出固定只取 500 行。改为分页循环导出全部匹配数据。
  16. **商品导入忽略分类列（中）**：CSV 表头包含分类，但导入时完全忽略。改为按分类名称查找 ID，不存在时该行失败并提示。
  17. **深层分类过滤失效（中）**：商品/库存/报表只匹配直接子分类，三级及更深分类不会被父分类查询命中。改用递归 CTE。
  18. **其他清理**：删除不存在的分类/商品/往来单位/仓库/账户返回 ErrNotFound；库存汇总 kinds 只统计非零库存；明细搜索支持商品编码；移除未使用的 `ctxToken`、`securityQuestion`、`CashFlowRow`、确认采购 `strict`、删除用户计数等死代码。

- 遗留问题 / 后续事项：
  1. **库存流水时间口径**：`stock_moves.created_at` 记录的是确认时间，报表日期筛选也按该字段。单据可回填历史日期，因此报表区间与业务日期可能不一致。彻底修复需要给 `stock_moves` 增加 `biz_date` 并做数据回填/迁移，本版本不做。
  2. **数据库迁移**：`schema.sql` 仍是 `CREATE TABLE IF NOT EXISTS`，没有版本化迁移，新增字段需要手工处理。
  3. **负库存成本**：允许负库存时出库成本会受结存金额限制；跨多次加权后作废冲销也可能产生小额成本偏差。属于现有成本模型限制。
  4. **SQLite 单连接**：单机 1～3 人场景足够，但不适合高并发/多机共享。
  5. **安全加固**：默认口令、HTTP 明文、无登录失败限流、Cookie 未设 Secure；建议在后续版本处理。
  6. **预警口径差异**：`ListStocks(low=true)` 仍只显示有库存记录的行，与 `LowStockList` 的零库存口径不同，后续可统一。
  7. **外键校验**：用户 role_id、商品 category_id 等仍依赖前端选择，后端未逐一校验存在性。
  8. **导出内存占用**：导出现在会取全量数据，但仍一次性放入内存，超大数据量可考虑流式写出。
  9. **前端测试**：仅覆盖纯函数，缺少组件与 E2E 测试。
